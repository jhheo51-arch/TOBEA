## 1. 제품과 프로젝트의 목적

FanBridge는 프로야구 팬의 반복 질문과 불편을 조사하고, 사람이 근거를 검토한 뒤 안내 화면과 응대 기준을 개선하며, 실제 참가자 과제로 자가 해결 효과를 확인하는 CX 실습 서비스다. CX는 예매·방문·문의 등 고객이 서비스에서 겪는 경험을 뜻한다.

핵심 흐름은 `자료 확보 → 문제·원인 후보 확인 → 개선 우선순위 결정 → 팬 안내·응대 기준 제작 → 실제 시험 → 사례 문서`다.

가장 중요한 학습 목표는 데이터를 근거로 문제를 정의하고 작은 개선을 실제 실행한 뒤, 결과와 한계를 설명하는 능력이다. 코드 작성과 자료 처리 구현은 Codex가 수행한다. 사용자에게는 방향 검토, 정책 판단, 실제 팬 조사와 결과 확인을 요청한다.

## 3. 대상과 첫 범위

- 팬 사용자: 경기 방문·예매·취소 상황에서 필요한 행동을 알고 싶은 팬. 처음 방문한 팬과 반복 방문 팬을 구분한다.
- 운영 사용자: 팬 질문을 정리하고 안내·응대 기준을 개선하는 실습자.
- 초기 조사 범위: KBO 팬의 예매, 변경·취소·환불, 입장·반입, 좌석·이동 관련 공개 경험 자료.
- 첫 실행 기본값: **LG 홈경기·잠실구장**. 사용자가 구단을 지정하지 않아 기획상 선택한 시작점이며, 불편이 더 크거나 자료가 더 많다는 조사 결과가 아니다.
- 잠실구장을 공유하더라도 LG·두산의 예매·환불 안내를 합치지 않는다. 구단, 홈·원정, 판매처, 적용일을 구분한다.
- 첫 개선은 문제 하나, 팬 안내 흐름 하나, 응대 가이드 하나로 제한한다. 문제 주제는 수집 근거를 보고 선택한다.
- 우천·취소 안내는 초기 가설 예시다. 문제가 확인되기 전에 실제 원인·개선 대상으로 확정하지 않는다.

자료 적합성 점검에서 한 연도 자료가 지나치게 적거나 정책 근거를 확보하지 못하면, 양 연도의 자료와 공식 안내를 확보할 수 있는 구단으로 범위를 바꾼다. 변경 이유를 최상위 작업일지와 분석 문서에 남긴다.

## 4. 해결할 문제와 검증 질문

문제 가설: 팬에게 필요한 정보가 흩어져 있거나 적용 조건이 모호해, 스스로 다음 행동을 정하기 어렵고 추가 질문이 생길 수 있다.

1. 2025·2026년 자료에서 어떤 관람 단계의 질문·불편이 반복되는가?
2. 안내를 찾지 못한 문제, 문장을 이해하지 못한 문제, 정책 자체의 문제를 구분할 수 있는가?
3. 두 연도에서 같은 문제가 나타나는가? 특정 공지·이벤트·구단에 국한되는가?
4. 안내와 응대 기준을 바꾸면 실제 참가자의 정답률·해결 시간·도움 요청이 달라지는가?

분석은 관찰, 가능한 설명, 아직 확인되지 않은 내용으로 나눈다. 팬의 감정·구매 여부·직관 경험을 댓글 내용만으로 확정하지 않는다.

## 5. 2025·2026년 데이터 설계

### 5.1 기간과 시점

- 기본 비교 기간: **2025-01-01~2025-09-29와 2026-01-01~2026-09-29**, 한국 시간으로 시작일 포함·다음 날 00:00 미만.
- 2026-09-30 당일 자료는 진행 중인 날짜이므로 기본 비교에서 제외한다.
- 2025년 전체 연도 자료는 보조 탐색에 활용하되, 2026년 진행분과 전체 건수를 직접 비교하지 않는다.
- 같은 달·같은 주제·같은 구단·같은 채널 기준의 비교를 우선한다. 개막·휴식·포스트시즌 등 시즌 단계도 기록한다.
- 작성 연도, 콘텐츠 게시 연도, 실제 경험 연도, 수집 시각을 별도로 저장한다. 경험 날짜를 모르면 미상으로 남긴다.
- 2025년에 게시된 글이라도 2024년 경험일 수 있다. 기본 연도 비교는 작성일 기준이며 경험 연도 비교는 확인 가능한 기록만 사용한다.
- 지금 확보한 과거 글은 당시 전체 자료의 복원이 아니다. 삭제·수정·비공개 자료가 누락된 현재 접근 가능 표본이다.

### 5.3 초기 표본 계획과 수집 판단

- 목표는 연도별 100건의 적합한 공개 경험 기록, 총 200건이다. 수집 전 설정한 탐색 목표이며 확보 건수가 아니다.
- 연도별 최소 30건, 각 연도 독립 콘텐츠 5개 이상의 맥락을 확보하면 제한적 비교를 진행한다. 이는 통계적 대표성을 보장하는 기준이 아니다.
- 부족하면 채널·검색어를 같은 기준으로 늘린다. 그래도 부족하면 연도별 정성 사례 비교로 전환하고 비율 증감 순위를 제시하지 않는다.
- 한 인기 콘텐츠가 전체 결과를 지배하는지 기록 수와 콘텐츠 수를 함께 보고한다. 서로 다른 콘텐츠에서도 재현되는지 확인한다.
- 검색어는 구단·구장과 예매, 취소, 환불, 입장, 반입, 좌석 등의 조합으로 사전에 고정한다. 추가 검색어와 목적 표집은 별도 표시한다.
- 광고·응원·선수 경기력 평가 등 방문·서비스 경험과 무관한 글은 제외하고, 정책 질문·구체적 행동·불편·반례를 남긴다.
- 중복은 출처 ID·정규화 URL로 제거하고 복사·재게시 기록은 연결한다. 한 기록에 여러 주제를 붙일 수 있어 주제 비율 합계가 100%를 넘을 수 있다.
- API 이용 조건과 자료별 분석·보관 허용 범위를 먼저 확인한다. 연결이 제한된 자료는 자동 수집을 우회하지 않고 다른 허용 자료나 동의받은 조사로 대체한다.

YouTube를 분석 자료로 채택할 수 있는 조건이 확인된 경우에만 최신순(time)·관련성순(relevance)을 각각 기본 100개까지 확보한다. relevance를 좋아요순이나 무작위 표본으로 부르지 않는다. 댓글 작성일을 직접 확인해 연도를 나누고 답글은 별도 수집·집계한다. 해당 정책 검토 전에는 YouTube 댓글 자동 분류·파생 지표를 제품 필수 기능에 넣지 않는다.

## 6. API 연결 방침

API는 외부 서비스에 정해진 방식으로 데이터를 요청하는 연결 통로다. API 키는 서비스를 사용할 때 제시하는 비밀 인증값이며 코드·화면·공유 문서에 넣지 않는다.

| 제공처 | 이번 프로젝트 용도 | 기획 결정 |
|---|---|---|
| 네이버 검색 API | 2025·2026년 후기의 제목·요약·링크·작성일 탐색 | 보조 발견 경로. 전체 본문·댓글 제공 및 과거 전체 검색을 가정하지 않음 |
| YouTube Data API | 영상 맥락·공개 댓글 접근 후보 | 연결 후보. 파생 데이터 제한·보관 조건 확인 전 자동 분석은 비활성 |
| API-Sports API-BASEBALL | KBO 경기 일정·결과 맥락 | 선택 기능. 2025·2026 시즌 응답·요금제·지연·상태 표현 확인 후 채택 |
| Sportradar Global Baseball | KBO 경기·시즌·과거 결과 맥락 | 대안. 계정 권한·과거 범위·라이선스·비용 확인 후 판단 |
| 기상청 ASOS 일자료 | 경기일의 과거 기온·강수 맥락 | 선택 기능. 관측소 매핑·누락 확인, 취소 여부는 공식 발표로 확인 |
| KBO 공식 웹페이지 | 관중·일정의 공식 확인 | 공개 웹자료. 이번 조사에서 일반 개발자용 공식 공개 API 문서는 확인하지 못함 |

인증이 필요한 실제 API 호출은 수행하지 않았다. 상세 확인 근거·제약·연결 전 시험은 별첨에 기록한다. 기본 제품은 사람이 확인한 자료를 표 형식 파일로 가져와도 완성할 수 있게 한다. 유료 스포츠 API와 외부 생성 AI 서비스는 필수 의존성으로 두지 않는다.

| 기능 | 사용자가 할 일 | 완료 기준 |
|---|---|---|
| 자료 가져오기 | 표 형식 파일 또는 허용된 API 배치 등록 | 필수 열·날짜·중복 검사, 오류 행과 가져온 수 안내, 원본 보존 |
| 자료 탐색 | 연도·구단·단계·채널·실제/합성 선택 | 모든 필터에 집계·근거가 함께 반영, 부족·미상·실패 표시 |
| 문제 검토 | 분류 후보 수정, 근거·반례 확인 | 원문 출처로 이동, 수정 전후와 이유 보존, 맥락 없는 요약을 확정하지 않음 |
| 비교 | 같은 기간의 두 연도 확인 | 분모·기간·출처 수 표시, 불일치 채널·조건 경고, 증감을 효과로 부르지 않음 |
| 개선 과제 | 문제 하나와 실행안 선택 | 근거·반례, 원인 후보, 선택 이유, 전후 흐름, 완료·판정 기준 필수 |
| 팬 안내 | 자신의 상황 선택 후 다음 행동 확인 | 적용 구단·판매처·정책 날짜·공식 링크 표시, 정보 부족 시 공식 문의 경로 안내 |
| 응대 가이드 | 같은 질문을 정책 근거로 답변 | 필수 확인 질문, 표준 답변, 금지할 단정, 예외 전달 기준 포함 |
| 실제 시험 | 과제 수행·결과 판정 | 익명 동의·화면 버전·배정·중단 기록, 합성 제외, 분모 0은 미측정 |
| 사례 문서 | 기획·실행·결과 내보내기 | 출처·방법·실제 관찰값·한계·본인 기여 포함, 미측정 자동 표시, 작성자 식별 정보 제외 |

자동 분석은 사람이 검토할 후보를 만드는 용도다. 외부 AI에 원문을 전송하는 기능은 첫 버전에 포함하지 않는다. 기본 분류·사람 검토만으로 작동하도록 한다.

## 8. 화면과 사용 흐름

운영자 화면은 ① 자료·수집 상태 ② 연도 비교·근거 ③ 문제 선택·개선 실행 ④ 시험 결과·사례 문서로 구성한다. 팬 화면은 상황 선택 → 조건 확인 → 행동 안내 → 해결 여부·추가 도움으로 구성한다.

예시: 팬이 취소 상황을 선택하면 홈구단·구매처·공식 취소 상태 등 필요한 조건을 확인하고, 검토된 정책에 따라 다음 행동과 공식 링크를 보여준다. 비가 온다는 이유만으로 경기 취소나 환불 여부를 자동 단정하지 않는다.

2025년 사례 분석 화면에는 당시 정책을 연결한다. 팬에게 현재 제공하는 안내는 현재 확인된 정책을 사용한다. 실험 화면에서 쓰는 과거 사례는 과거 상황임을 명시한다. 공식 구단 서비스로 오인되지 않게 개인 CX 실습 서비스라고 표시한다.

## 9. 우선순위 결정

첫 개선 후보 3개는 ① 취소·환불 조건 이해 ② 입장·반입 조건 이해 ③ 예매·좌석 변경 안내다. 아직 실제 불편으로 확정하지 않는다.

우선 문제는 빈도뿐 아니라 서로 다른 출처의 재현, 행동의 구체성, 오류 시 팬에게 미치는 영향, 공식 정답 확보, 직접 변경 가능성을 보고 선택한다. 각 항목 판단과 근거를 남긴다. 많이 언급된 문제라도 공식 정책을 확인할 수 없거나 우리가 바꿀 수 없다면 첫 실행에서 제외한다.

## 10. 성과 측정과 실제 팬 시험

2025·2026년 비교는 문제 발견용이다. **개선 효과는 같은 조건에서 기존 안내와 개선 안내를 사용한 실제 참가자의 행동으로 측정한다.**

### 10.1 첫 시험 설계

- 준비 조사: 동의받은 팬 5명 이상 인터뷰를 목표로 실제 질문과 안내의 혼란을 확인한다. 달성 전에는 모집 계획으로 표시한다.
- 본 시험: 실제 팬 20명, 기존 안내 10명·개선 안내 10명을 목표로 한다. 인원은 탐색적 시험 목표이며 통계적 검정력 계산 결과가 아니다.
- 첫 방문·반복 방문 경험군의 균형을 맞추고 군 안에서 무작위 배정한다. 같은 참가자는 한 조건에서만 시험한다.
- 두 조건에서 같은 과제, 기기 조건, 정책 버전, 제한 시간(과제당 5분)을 적용한다. 정책 검토자가 시험 전에 정답·부분 정답·오답 기준을 확정한다.
- 대표 과제 3개는 선택한 문제의 정상 상황·조건 차이·예외 상황을 포함한다. 답변과 다음 행동을 함께 확인한다.
- 실제/시험 자료를 분리하고, 익명 참가자의 본인 동의·사용 경험만 기록한다. 보상 여부·모집 경로도 남긴다.
- 중단자를 전체 배정 인원에서 삭제하지 않는다. 기술 장애는 사전 정의한 별도 사유로 기록하고 포함·제외 결과를 모두 확인한다.

### 10.2 지표 정의와 잠정 목표

| 지표 | 정의 | 초기 판단 기준 |
|---|---|---|
| 주 지표: 자가 해결 성공률 | 추가 도움 없이 3개 과제 모두 제한 시간 내 정답인 참가자 / 전체 배정 참가자 | 개선 조건이 기존보다 20%p 이상 높음 |
| 도움 요청 비율 | 한 번 이상 추가 도움을 요청한 참가자 / 전체 배정 참가자 | 개선 조건에서 낮아짐 |
| 과제 해결 시간 | 시작부터 답 제출까지. 성공자 중앙값과 전체 완료·중단·시간초과 수를 함께 표시 | 성공자 중앙값 20% 이상 단축, 성공률 저하 없음 |
| 위험한 오답 | 금전·입장 등 잘못된 행동을 유도하는 답의 실제 건수 / 전체 제출 답 수 | 개선 안내의 정책 오류 0건, 팬 위험 오답 증가 없음 |
| 답변 품질 | 사전 평가표의 정확성·조건 확인·다음 행동·예외 전달 점수 | 정확성 필수 항목 전부 충족 |

%p는 두 비율의 차이다. 예를 들어 40%→60%는 20%p 상승이다. 목표는 설계한 판단 기준이며 달성한 성과가 아니다. 소규모 비무작위 모집의 결과는 참여자 범위에서 해석하고 모집 편향·불확실성을 함께 보고한다. 목표를 못 넘겨도 원인과 다음 개선을 기록한다.

실제 고객센터 자료를 확보한 뒤에만 `방문/거래 대비 문의율`, `같은 문제의 재문의율`, `처리 시간`, `응답 기준 시간 내 처리 비율`, `상담 후 만족도`를 추가한다. 예: 문의율은 실제 문의 수/확인된 거래 수로 분모·기간·중복 규칙을 고정한다. 재문의는 익명화된 동일 고객·동일 이슈의 7일 이내 재접촉 등 정의를 확정한다. 안내 시험만으로 실제 문의가 감소했다고 쓰지 않는다.

## 11. 기술·운영 요구

- 첫 버전은 컴퓨터에서 실행하는 웹 서비스와 로컬 SQLite 저장소(한 파일에 자료를 담는 데이터 저장 방식)로 시작한다. 공개 게시·유료 가입은 이번 PRD 범위에 포함하지 않는다.
- 수집, 분류, 정책, 개선, 시험을 서로 연결하되 원본과 수정 기록을 분리한다. 파일 가져오기와 API 연결에 같은 검증 규칙을 적용한다.
- API 키는 서버 쪽 설정값으로만 읽고 오류 기록·화면·내보내기에서 제외한다. 외부 요청의 실패·할당량 소진·중단 후 재개 상태를 표시한다.
- 원문은 실행 명령이 아니라 분석 자료로 처리한다. 화면에 표시할 때 포함된 코드·링크를 임의 실행하지 않는다.
- 모바일 화면에서도 상황 선택과 공식 링크 확인이 가능해야 한다. 긴 자료는 접어서 보여주고 키보드로 주요 입력·버튼을 사용할 수 있게 한다.
- 출처별 보관 조건을 적용한다. 장기 연구용 과거 사본이 허용되지 않으면 갱신·삭제 상태를 남기고 영구 보관을 가정하지 않는다.
- 연락처·작성자 계정 등 불필요한 식별 정보는 수집·공유하지 않는다. 팬 인터뷰는 동의 범위·삭제 요청을 관리하며 공개 문서에는 짧은 익명 근거만 넣는다.

## 12. 구현 순서와 각 단계의 산출물

1. 자료 적합성 점검: 연도별 접근 가능 사례·정책·이용 범위 확인, 실제 API 표본 응답 점검. 결과는 데이터 출처 문서에 추가한다.
2. 2025·2026년 분석: 동일 기준으로 정제·분류하고 근거·반례가 있는 문제 후보 3개를 작성한다.
3. 문제 하나 선택·개선 제작: 팬 안내 화면과 응대 가이드, 전후 흐름, 판정 기준을 만든다.
4. 실제 팬 시험: 모집·배정·관찰·판정 기록과 전후 결과를 남긴다.
5. 포트폴리오 사례: 공고 요건과 연결해 문제·선택·실행·효과·기여·한계를 설명한다.

각 결과물은 새 버전으로 보존한다. 진행 기록은 스타터 킷 최상위 작업일지.md 하나에 덧붙인다. 실제 모집 기간은 참가자 확보 상황에 따라 정하며 완료일을 임의 약속하지 않는다.

## 13. 출시 전 확인과 범위 제외

첫 실행 완료 기준은 두 연도의 적합 자료·누락 상태를 확인할 수 있고, 근거가 연결된 개선 하나가 팬 화면과 응대 가이드에 반영되며, 실제/합성 시험을 분리 저장하고 미측정 상태로도 사례를 내보낼 수 있는 것이다. 실제 효과 검증 완료는 실제 참가자 시험·정답 검토·분모 확인까지 마친 상태다. 둘을 구분한다.

핵심 검사는 연도 경계·중복 제거·복수 라벨 분모, 정책 적용일·구단 혼동 방지, 중단자 포함·합성 제외·분모 0, 저장·내보내기 식별 정보 제외, 모바일 안내 동작을 확인한다.

첫 범위에서 제외: 전체 구단 통합 운영, 실시간 고객센터 대행, 자동 환불·보상 결정, 경기 취소 예측, 상담 인력 배치, 구매 이력 기반 재방문 예측, 검증되지 않은 AI 자동 답변, 공개 배포. 문의량 예측·인력 계획은 실제 처리 이력을 확보한 뒤 확장한다.

## 14. 현재 확정된 것과 남은 확인

확정: 제품 방향, 2025·2026년 비교, 초기 범위·선택 기준, 팬 안내와 응대 가이드, 실제 검증 설계, 완료 기준.

남은 확인: 연도별 실제 적합 자료 수, 역사적 정책의 접근 가능성, API 인증·시즌별 응답·이용 권한, 조사 참가자 확보. 이는 실행 시 확인할 조건이며 현재 확보·실행 완료로 표시하지 않는다.

이번 기획의 결과는 **채용 역량과 연결된 실행 가능한 PRD**다. 팬 데이터 분석 결과나 개선 성과는 아직 없다.
