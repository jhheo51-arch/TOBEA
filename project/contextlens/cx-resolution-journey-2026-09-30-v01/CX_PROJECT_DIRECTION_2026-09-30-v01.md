# CX 프로젝트 방향: 고객의 문제 해결 경로와 재문의 원인

작성일: 2026-09-30 · 상태: 조사 기반 제안, 실제 고객 데이터 분석·개선 효과 검증 전

## 1. 공고에서 확인한 역할

토스씨엑스 [CX Planning Manager 공고](https://toss.im/career/job-detail?job_id=7528516003)는 상담 데이터에서 반복·오류 문의의 원인을 찾고, 화면 흐름·기능 정의서로 개선안을 만들며, 제품·정책·운영팀과 협업해 실행한 뒤 효과를 측정하는 사람을 찾는다. SLA(약속한 응대 수준)와 CSAT(상담 후 고객 만족도)를 언급하며, 고객 여정·상담 흐름·문의 유입 구조의 이해를 요구한다. 현재 공고는 **CX 경력 5년 이상**을 명시한다. 이 프로젝트만으로 그 경력 요건을 대체할 수는 없다.

이 공고의 핵심은 챗봇 제작 자체보다 **문제 정의 → 근거 → 우선순위 → 화면·정책·상담 흐름 개선 → 효과 검증**의 연결이다. SQL은 공고에 명시된 필수 요건이 아니다. 다만 데이터 정의와 집계 과정을 재현 가능하게 보여주면 분석 역량을 설명하기 좋다.

## 2. 추천하는 단일 프로젝트

**질문: 고객은 문제를 해결하려고 어떤 경로를 거치며, 어디에서 해결에 실패해 다시 문의하는가?**

첫 사례는 금융 서비스의 한 가지 문제 상황으로 좁힌다. 예를 들어 ‘송금이 실패했을 때 다음 행동을 찾는 과정’을 후보로 삼는다. 특정 회사에서 이 문제가 많이 발생한다는 뜻은 아니다. 공개 자료와 실제 서비스의 도움말 구조를 먼저 조사해 주제를 확정한다.

최종 산출물은 앱이 아니라 **반복 가능한 CX 조사 노트와 개선 제안서**다. 한 주제마다 고객 여정 지도, 문의 유형표, 지표 정의, 근거 자료, 우선순위, 개선 화면 흐름, 소규모 사용성 시험 결과를 같은 형식으로 쌓는다. 한 달에 사례 하나를 추가하면 경험의 축적 과정이 보인다.

## 3. 자료를 확보하는 두 경로

| 자료 | 확인할 수 있는 것 | 한계 |
|---|---|---|
| 공개 금융 민원 자료(CFPB 등) | 접수 날짜, 상품, 문제·세부 문제, 접수 경로, 회사 응답 등에서 문제 후보 탐색 | 미국 자료이며 전체 고객의 대표 표본이 아니다. 개별 앱의 통화 길이·챗봇 이용·재문의 여부를 알 수 없다. |
| 공개 도움말·고객 지원 화면 | 고객이 정보를 찾는 경로, 안내 문구, 상담 전환 지점 | 실제 이용자 행동이나 문의 감소 효과를 알 수 없다. |
| 동의받은 소규모 사용성 시험 | 주어진 문제를 해결했는지, 걸린 시간, 잘못 해결했다고 믿었는지, 어디에서 헤맸는지 | 소수 참가자의 관찰이다. 실제 문의량·SLA·CSAT 개선을 입증하지 않는다. |
| 회사 내부 상담 자료에 접근할 수 있는 경우 | 문의 시각·채널·유형·처리 상태·재문의와 같은 운영 지표 | 접근 권한, 개인정보 보호, 연결 가능한 식별자와 기록 방식부터 확인해야 한다. |

공개 민원에서 ‘빈도가 높은 문제’를 고르더라도 이용자 수가 많은 서비스의 민원이 더 많을 수 있다. 따라서 민원 건수를 곧바로 **발생률**로 해석하지 않는다.

## 4. 상담 데이터를 얻는다면 먼저 그릴 구조

분석의 기본 단위는 **한 번의 문의 사건**이다. 채널(전화·채팅·메일·카카오톡 등), 문의 ID, 익명 고객 ID, 접수·첫 답변·종료 시각, 상담사 분류, 고객이 실제로 해결했는지, 재문의 여부를 구분한다. 상담 한 건에 주제가 여러 개일 수 있어 유형은 별도 표로 관리한다. 도움말 보기·챗봇 대화·상담 전환은 같은 고객 여정으로 연결할 수 있는지 확인한다.

전화의 ‘4분 통화’는 통화 시작·종료 시각 또는 통화 길이 기록에서 계산할 수 있지만, 모든 회사가 같은 항목을 저장한다고 가정할 수 없다. 음성 파일이 있어야 녹취를 텍스트로 바꿀 수 있고, 변환 결과의 오류를 사람이 확인해야 한다. 채널톡은 상담 태그·상담 시간·만족도 등 일부 자료와 파일 다운로드 기능을 문서화한다. 실제 이용 가능 항목은 도구 설정과 권한에 따라 확인해야 한다.

자동 분류는 상담사 분류와 **불일치 사례를 검토하는 보조 도구**로 먼저 시험한다. ‘AI가 90% 답변’이라는 수치는 현재 근거가 없으므로 목표치로 쓰지 않는다. 봇이 답한 뒤 고객이 전화했다면 해결로 세지 않는다.

## 5. 지표 정의 예시: 실제 프로젝트에서는 조건을 먼저 확정

| 질문 | 지표 예시 | 필요한 자료·주의점 |
|---|---|---|
| 답을 제때 받았나? | 첫 답변 SLA 준수율 = 약속한 시간 안에 첫 **사람 답변**을 받은 문의 / 대상 문의 | 시작·첫 답변 시각, 운영 시간, 채널별 약속 기준. 자동 확인 메시지를 답변으로 셀지 결정해야 한다. |
| 고객이 만족했나? | CSAT = 만족 응답 수 / 만족도 설문 응답 수 | 설문 미응답자가 있으므로 전체 고객 만족률로 해석하지 않는다. |
| 해결됐나? | 재문의율 = 종료 후 7일 안에 같은 문제로 다시 문의한 고객 / 해당 문제로 종료한 고객 | 익명 고객 ID와 문제 ID가 연결되어야 한다. 채널을 바꿔 연락한 경우도 포함해야 한다. |
| 문의 자체가 줄었나? | 문의율 = 해당 문제 문의 수 / 관련 기능 이용 또는 시도 수 | 이용 규모·시즌성 변화를 같이 봐야 한다. 원시 문의 건수만 비교하지 않는다. |
| 스스로 풀었나? | 도움말/안내를 거친 과제 성공률 = 정확히 과제를 마친 시험 참가자 / 과제를 시작한 참가자 | 공개 서비스 시험과 실제 운영 지표를 구분한다. ‘문의 안 함’만으로 해결을 단정하지 않는다. |

## 6. 첫 조사 회차와 이후 반복

1. 공개 민원·지원 자료를 읽고 **문제 상황 하나**를 정한다. 자료 출처와 선택 근거를 남긴다.
2. 고객이 문제 인지 → 정보 탐색 → 도움말/봇 → 사람 상담 → 해결 확인으로 이동하는 경로를 그린다. 확인된 흐름과 추정 흐름을 다르게 표시한다.
3. 시험 참가자에게 실제 계정·송금·개인정보 입력 없이 가상 상황을 제시한다. 현재 안내에서 답을 찾는 과제와 개선한 안내에서 답을 찾는 과제를 비교한다.
4. 과제 성공·시간·오답을 정답으로 믿은 경우·도움 요청 의도를 기록한다. 사용자의 말은 동의 범위 안에서 익명 요약한다.
5. 원인이 안내 부족인지, 화면 흐름인지, 정책·시스템 한계인지 나누고 **가장 근거가 큰 개선안 하나**를 화면 흐름도와 기능 정의로 적는다.
6. 같은 측정 기준으로 다시 시험하고 결과·한계를 기록한다. 다음 달에는 다른 문제 상황에 같은 틀을 적용한다.

실제 서비스의 문의 감소나 고객 만족도 개선은 회사 내부 자료와 실제 반영 이후의 비교가 있어야 주장할 수 있다. 이 프로젝트의 첫 회차는 **조사·기획·시험 역량**을 보여주는 범위로 제시한다.

## 7. 포트폴리오에서 보여줄 증거

- **기획**: 고객 여정 지도, 문제 원인과 우선순위, 개선 전후 화면 흐름, 제품·운영·정책팀별 실행 항목.
- **데이터 활용**: 자료 출처, 분석 단위, 분모와 분자, 누락 데이터, 시험 기록과 비교 결과.
- **판단의 정직성**: 공개 민원은 문제 탐색 자료, 소규모 시험은 사용성 근거, 실제 운영 개선은 아직 검증 전이라고 구분.
