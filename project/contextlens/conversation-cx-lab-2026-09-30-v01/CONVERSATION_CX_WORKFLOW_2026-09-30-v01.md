# 혼자 쌓는 CX 경험: 대화 → 맥락 → 반복 문제 → 개선 → 검증

작성일: 2026-09-30 · 상태: 첫 분석 자료 선택 전

## 목적

**고객경험(CX)**은 사람이 서비스를 접하면서 목표를 이루거나 막히는 과정 전체다. 상담 대화뿐 아니라 인터뷰, 서비스 후기, 공개 댓글, 사용성 시험 중 나온 말과 행동도 관찰 자료가 된다. 이 작업은 ‘말을 많이 한 주제’를 세는 데서 멈추지 않고 **사람이 하려던 일 → 왜 막혔는지 → 어떻게 해결을 시도했는지 → 실제 결과**를 연결한다.

이 폴더는 매번 같은 질문과 기록 기준을 써서 스스로 조사 경험을 쌓기 위한 시작점이다. 토스씨엑스 공고의 문제 정의·개선 실행·효과 검증 흐름을 참고하되, 특정 회사의 실제 성과를 주장하지 않는다. [참고 공고](https://toss.im/career/job-detail?job_id=7528516003)

## 한 회차의 분석 단위

**한 사람이 하나의 목표를 달성하려 한 사건**을 기본 단위로 삼는다. 한 대화에 여러 문제가 섞이면 문제별로 나누되, 원래 대화와 순서를 찾을 수 있게 사건 ID를 남긴다. 같은 사람의 여러 접촉을 연결할 권한과 식별 정보가 없다면 ‘재문의’라고 단정하지 않는다.

분석 범위는 처음에 **한 서비스, 한 문제 상황, 정해진 기간**으로 제한한다. 예: ‘회원가입 중 인증에 막힌 사람의 도움 요청, 9월 한 달’. 자료의 출처, 몇 건을 보았는지, 무엇을 제외했는지를 적는다. 공개 후기나 자발적 제보는 전체 이용자를 대표하지 않는다.

## 7단계 워크플로우

| 단계 | 할 일 | 남길 증거 | 끝났다고 볼 기준 |
|---|---|---|---|
| 1. 질문 정하기 | ‘누가 어떤 목표에서 어디에 막혔나?’를 한 문장으로 쓴다. | 대상·상황·기간·자료 범위 | ‘서비스가 나쁘다’처럼 넓은 판단이 아니라 확인 가능한 질문이 된다. |
| 2. 자료 모으기 | 권한 있는 대화·인터뷰·후기·시험 기록을 모으고 출처를 남긴다. | 사건 ID, 날짜, 출처, 대화 순서, 누락 정보 | 원문과 메모를 다시 연결할 수 있다. |
| 3. 맥락 읽기 | 발화 전후를 읽고 목표, 직전 행동, 기대, 장애물, 해결 시도, 결과를 분리한다. | 사건별 짧은 여정 요약과 근거 발화 | 단어만 보고 감정·원인을 확정하지 않는다. |
| 4. 유형 붙이기 | 같은 의미의 문제를 묶고, 새 유형은 정의를 적는다. AI는 후보를 제안할 수 있지만 사람이 확인한다. | 유형 이름·포함/제외 기준, 검토한 사건 ID | 다른 날 다시 봐도 비슷하게 분류할 수 있다. |
| 5. 우선순위 정하기 | 반복 정도와 고객 피해, 해결 실패, 고칠 수 있는 범위를 함께 본다. | 건수/분모, 대표 사례, 반례, 불확실성 | ‘많이 보인다’와 ‘중요하다’를 구분한다. |
| 6. 개선안 시험 | 안내 문구·화면 흐름·정책·상담 절차 중 원인에 맞는 것 하나를 바꿔 시험한다. | 변경 전후, 사용성 과제, 성공 여부·시간·오답 | 바뀐 것과 비교 기준을 설명할 수 있다. |
| 7. 결론 남기기 | 확인된 변화, 아직 모르는 점, 다음 회차의 질문을 쓴다. | 한 장의 사례 요약과 결정 | 실제 개선을 했는지, 시험만 했는지 구별된다. |

## 반복·핵심·맥락을 구분하는 법

- **반복**: 같은 문제 유형의 사건 수를 센다. 대화 메시지 수를 세면 말이 긴 사람의 문제가 과대평가될 수 있다. `해당 유형 사건 수 / 검토한 전체 사건 수`처럼 분모를 함께 적는다.
- **핵심**: 빈도만 보지 않는다. 소수라도 돈·신뢰·접근성·해결 실패에 큰 영향을 주면 우선순위가 높을 수 있다. 우선순위 선정 이유와 반대 근거를 남긴다.
- **맥락**: ‘환불’이라는 단어가 같아도 ‘신청 방법을 몰랐다’, ‘처리 상태를 알 수 없었다’, ‘정책상 불가능했다’는 다른 문제다. 고객이 하려던 일과 직전 행동, 서비스 응답, 이후 결과까지 읽는다.
- **원인**: 대화에서 관찰한 사실과 원인 가설을 분리한다. ‘고객이 버튼을 못 찾았다’는 관찰일 수 있지만 ‘버튼 위치가 원인’은 추가 시험이 필요한 가설이다.

## 자료별로 할 수 있는 분석

| 자료 | 가능한 질문 | 조심할 점 |
|---|---|---|
| 동의받은 인터뷰·사용성 시험 | 왜 그렇게 행동했는가, 실제로 과제를 풀었는가 | 소수의 응답을 전체 고객 비율로 쓰지 않는다. |
| 공개 후기·댓글 | 반복적으로 언급되는 불편의 후보는 무엇인가 | 작성자의 상황과 전체 이용자 수를 알기 어렵다. |
| 본인이 운영한 서비스의 상담·메일·채팅 | 문의 유형, 해결 흐름, 재접촉 후보 | 이용 목적·권한·개인정보를 확인하고 원문 공개는 피한다. |
| 챗봇·자동응답 대화 | 사람이 넘어온 지점과 봇이 이해 못 한 질문은 무엇인가 | 봇이 대화를 닫았다고 실제 해결로 세지 않는다. |
| 가상 대화 | 분류 연습과 양식 시험 | 실제 고객 문제·개선 효과의 증거로 쓰지 않는다. |

## 기록할 최소 항목

사건 ID / 자료 출처 / 관찰 날짜 / 고객의 목표 / 직전 상황 / 핵심 발화의 익명 요약 / 서비스·상담의 응답 / 고객의 다음 행동 / 확인된 결과 / 문제 유형 / 근거 수준(직접 관찰·고객 진술·분석자의 추정) / 개인정보 제거 여부.

전화 길이나 응답 시간은 실제 시작·종료 기록이 있을 때만 계산한다. 음성을 글로 바꾼 자료는 잘못 받아쓴 부분을 확인한다. 서로 다른 채널의 대화를 연결할 수 없으면 같은 고객의 여정이라고 주장하지 않는다.

## 첫 회차의 현실적인 완료 기준

1. 권한 있는 자료 10~20건 또는 동의받은 인터뷰·사용성 시험 3~5건 중 확보 가능한 범위를 명시한다. 숫자는 학습용 시작 범위이며 통계적 대표성을 뜻하지 않는다.
2. 사건마다 고객 목표·막힌 지점·결과를 기록하고 문제 유형의 기준을 만든다.
3. 가장 근거가 큰 문제 **하나**를 고르고 화면·안내·절차 개선안을 작성한다.
4. 같은 과제를 사용해 개선안 전후를 관찰한다. 실제 서비스에 반영하지 않았다면 ‘사용성 시험 결과’로만 발표한다.

첫 자료가 정해지기 전에는 건수, 핵심 유형, 개선 성과를 채우지 않는다. 반복 사례가 쌓이면 회차별로 ‘무엇을 수정했고 판단이 어떻게 바뀌었는지’가 CX 경험의 증거가 된다.

## 자료 취급 기준

개인 대화·연락처·계좌 정보·음성 원본을 외부 도구나 공개 포트폴리오에 임의로 올리지 않는다. 분석할 권한과 참가자의 동의 범위를 확인하고, 공개 결과에는 식별 가능한 원문 대신 익명 요약을 쓴다. AI를 쓴 경우 **AI가 제안한 유형 / 사람이 확인한 유형 / 불일치 사례**를 따로 기록한다.
